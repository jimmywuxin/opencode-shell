# opencode-shell 改进清单（2026-11-03）

> 来源：对照 `dsh-shell` / `LibreTV-shell` 的横向审查。
> 本文只列 **opencode-shell 自己要做** 的部分，另两个项目的同类项在各自仓库的文档里。
> 执行方式：Jimmy 单独指某个编号，再动手；一次一个编号、单独 commit。

## 优先级定义

| 级别 | 含义 |
|---|---|
| **P0** | 真会坏：会导致服务反复重启、白屏、错位，用户无法自救 |
| **P1** | 体验/排障：能自救但成本高 |
| **P2** | 工程卫生 |

## 现状基线

- 壳：`src/ShellApp.swift`（488 行，三个壳里最精简）
- 服务：launchd `ai.opencode.web` → `src/supervisor.sh`（前台常驻，20s 探活）→ `opencode service start`
- 启动：`src/launcher.sh --url`（kickstart → bootstrap → nohup 三级兜底）→ 打印 pair 链接
- 认证：`opencode pair` 一次性链接，服务端 302 + Set-Cookie 种 30 天会话
- **本项目的定位**：三个壳里服务层最成熟（supervisor + 二进制指纹换血），这套机制是另两个项目应该来抄的。

## P0-1 supervisor 与 launcher 的就绪判据不一致（302）

**位置**：
- `src/launcher.sh:56-59`：`ready()` 认 `200|204|302|401`
- `src/supervisor.sh:53-57`：`alive()` 只认 `200|401`

**现象**：同一条 loopback 请求，launcher 认为「就绪」，supervisor 认为「挂了」。服务一旦进入返回 302 的状态（例如内部重定向到 pairing 页），supervisor 每 20s 判定一次死亡 → `service stop` → `sleep 2` → `service start` → 端口还没准备好 → 下一轮继续判死。

**影响**：
- 服务被自己人反复重启，稳定性比「没有 supervisor」更差。
- `supervisor.log` 被「服务无响应，重启托管服务」刷屏，真实病因被淹。
- 用户侧表现：页面时好时坏，连接断断续续。

**改法**：抽一个共同判据，两边都用。最小改动是让 `alive()` 与 `ready()` 完全一致：
```bash
alive() {
  local code
  code="$(curl -s -o /dev/null -w "%{http_code}" --noproxy '*' --max-time 3 "$URL/" 2>/dev/null)"
  case "$code" in 200|204|302|401) return 0 ;; esac
  return 1
}
```
更彻底的做法（推荐，但可后置）：`launcher.sh` 与 `supervisor.sh` 的 `resolve_oc` / `probe` 已经重复了 60 行，抽成 `src/common.sh`，两个脚本 source 同一份判据 —— 判据分叉正是因为没有单一来源。

**验收**：
1. 手工让服务返 302（或造一个返回 302 的探针），20s 周期内**不出现** `服务无响应，重启托管服务`。
2. 真把服务停掉（`opencode service stop`）→ 一个周期内自动重启，日志只有一条重启记录。

## P0-2 WKWebView 内容进程崩溃后永久白屏

**位置**：`src/ShellApp.swift`（AppDelegate 缺 `webViewWebContentProcessDidTerminate`）

**现象**：内容进程被回收时窗口停在白屏。opencode 是长会话、长输出的应用（大段代码渲染 + 长对话），页面内存压力大。

**影响**：白屏后只能 ⌘Q 重开；更糟的是重开时会重新 mint 一个 pair 链接（见 P1-3），会话上下文也丢了。

**改法**：
```swift
func webViewWebContentProcessDidTerminate(_ webView: WKWebView) {
    shellLog("web content process terminated: reloading")
    webView.reload()      // cookie 存 .default()，reload 不掉登录
}
```
- 5s 冷却，最多 2 次，防页面本身必崩时无限重载。
- 重载仍失败 → 走 `connect()`（重新 pair）。

**验收**：
1. `kill -9` WebKit `WebContent` 子进程 → 1-2s 内自动恢复且**不掉登录**。
2. `shell.log` 有 `web content process terminated`。

## P0-3 全屏退出后标题栏/交通灯错位

**位置**：`src/ShellApp.swift:138`（`window.contentView = webView`）

**现象**：`isElementFullscreenEnabled = true` 已开，但 WebKit 元素全屏进出后可能残留 `.fullSizeContentView`，标题栏变浮层、交通灯错位。

**影响**：`LibreTV-shell` 已踩过并写好完整修法（容器承载 + baseline 相对几何判据 + 四级修复 + 冷却重试），本项目一行都没接。

**改法**：
1. 容器承载：`NSView` 装 `webView` + `autoresizingMask`，`window.contentView = container`（直接当 contentView 时全屏退出 frame 账会算错）。
2. 移植 `captureHealthyBaseline` / `titleBarIsBroken` / `scheduleTitleBarRepair` / `repairTitleBarIfNeeded`，挂到 `windowDidExitFullScreen` / `windowDidResize` / `windowDidBecomeKey`。
3. 本项目没有标题栏透明/动态底色，移植时可以把 dsh 的 chrome 相关分支全部去掉，比 dsh 更好落地。

**验收**：
1. ⌃⌘F 全屏进出 3 次 → 交通灯位置不变、标题栏高度 ≈28pt。
2. 拖窗口大小 20 次，不跑偏。
3. `shell.log` 无 `repair failed: still broken`。

## P1-1 ⌘R 现在等于「重跑 launcher + 重新 pair」

**位置**：`src/ShellApp.swift:360`（`reloadPage` → `connect()`）

**现象**：⌘R 会跑 `launcher.sh --url`：探活 → 取一次性 pair 链接 → 加载 → 302 种 cookie。比单纯刷页面重得多，还会打断当前页面状态。

**改法**：
- ⌘R → `webView.reload()`（快路径，cookie 已持久化，不掉登录）
- ⇧⌘R → `connect()`（慢路径：重跑 ensure + 重新 pair）
- 菜单文案跟进：「重新载入」/「重新连接」。

**验收**：⌘R 立即刷新且不产生 `connect: url acquired` 日志。

## P1-2 缺排障入口（重启服务 / 打开日志 / 服务状态）

**位置**：`src/ShellApp.swift:buildMenu()`（`:249-358`）

**现象**：出问题时用户只能开终端看 `~/.local/share/opencode/log/`（里面还有 `supervisor.log`、`web.err.log`），壳自己不说当前是什么状态。

**改法**：视图菜单加：
- 「重启服务」→ `launchctl kickstart -k gui/$UID/ai.opencode.web`，等 5s 后 `connect()`
- 「打开日志」→ `NSWorkspace.open` 打开 `shell.log`；子菜单放 `supervisor.log` / `web.err.log`
- 「服务状态」→ HTTP 码 + launchctl 是否托管 + 端口 PID，`NSAlert` 一行结论

**注意**：日志打开路径必须走 `redactSecrets` 之外（打开文件不涉及内容），但**不要把带 token 的 URL 写进任何日志**这条纪律继续保持。

**验收**：`launchctl bootout gui/$UID/ai.opencode.web` 后点「重启服务」，壳自动恢复加载，无需终端。

## P1-3 每次 `connect()` 都 mint 新 pair token，旧的无人回收

**位置**：`src/launcher.sh` 的 `pair_url()`（每次 `--url` 都跑 `opencode pair`）

**现象**：pair 链接带一次性 token。⌘R（现在 = 重连）、启动失败重试、每次冷启动都会生成新的；服务端是否清理过期 token 未知。日志侧已脱敏，但服务端可能积累无效会话。

**影响**：目前是「轻微不卫生」而非故障。但如果服务端有 token 数量上限或过期清理策略，长期开机会撞上。

**改法**（低风险）：
1. 壳侧优先复用：已持久化的 cookie 若仍有效（页面能加载），就不调 `pair_url`，直接用裸 `http://127.0.0.1:49374/`。
2. launcher 加 `--url-only` 分支：只返回裸 URL、不做 pair；壳在 cookie 有效时用这条路。
3. 真需要重新 pairing 时才 mint。

**验收**：连续冷启动 5 次，`opencode pair` 调用次数 ≤ 1（cookie 有效期间）。

## P2-1 与另两个项目抽公共骨架

**现状**：`buildMenu`（约 110 行）、`loadMessagePage`、`escapeHTML`、`shellLog`、下载处理、`windowShouldClose` 与另两个项目几乎逐字相同。

**本项目额外资产**：`redactSecrets`（`:50-57`）是三个壳里唯一的日志脱敏实现，抽公共骨架时**必须**把它带过去，dsh 的日志目前是完全不脱敏的。

**改法**：先定分发方式（独立 `shell-kit` 仓库 or 三处 vendored 副本 + 同步脚本），再动手。

## P2-2 端口 49374 出现在四个地方

**位置**：`src/ShellApp.swift:22`（`baseURL`）、`src/launcher.sh`（`PORT=49374`）、`src/supervisor.sh`（`PORT=49374`）、`src/ai.opencode.web.plist`（启动参数里的端口）

**问题**：换端口要同步四处，漏一处就是「壳连不上、服务好好跑着」。

**改法**：`Info.plist` 加 `OpencodeServiceURL`，壳从 bundle 读；脚本侧抽 `common.sh` 里一个 `PORT` 常量（与 P0-1 的判据合并一起做最划算），plist 渲染时同源。

## 这个项目的「资产」——别在重构里弄丢

1. **supervisor 二进制指纹换血**（`supervisor.sh` 的 `fp()` / `restart_service`）：`stat -L -f '%m-%z'` 跟软链取 mtime+size，npm 升级后自动重启 daemon 加载新版本。这是三个壳里唯一解决「升级后还跑旧二进制」的实现，dsh 靠人工 `dsh-restart`。
2. **`redactSecrets`**：唯一有日志脱敏的壳。
3. **launcher 的 stdout 契约**（只有 URL、诊断走 stderr）：解析逻辑干净，值得复制到另两个项目。

## 改动约束（每条都适用）

1. **改完必须 `bash build.sh`**：`launcher.sh` / `supervisor.sh` / plist 会被安装到 `.app` 内与 `~/Library/LaunchAgents/`，只改 `src/` 不重建 = 跑的还是旧脚本。
2. 动 plist 后必须 `launchctl bootout` + `bootstrap` 才生效，并确认 `launchctl print` 显示 `state = running`。
3. **`launchctl bootstrap` 在 WorkBuddy 派生的 shell 里必报 `5: Input/output error`**（沙箱限制），要验证请从 `.app` 触发或在用户终端里跑。
4. pair token 等同登录凭据：任何新增日志路径都必须过 `redactSecrets`，不得记录 URL 全文。
5. 破坏性操作先提案；旧 `.app` 进废纸篓。
6. 真机验收，不接受「编译通过即完成」。
7. 版本号：修复合到 patch，小改动不单独发版。
